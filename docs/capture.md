# 报文分析实验

## 在 Windows 上捕获本机流量

1. 在用于演示的电脑上安装官方 Npcap。使用普通网络接口或 Npcap 回环接口即可。如果安装时启用了仅限管理员捕获，请用获授权的账户启动 NetScope。驱动安装完成后重启应用。[Npcap 安装程序](https://npcap.com/#download) · [用户指南](https://npcap.com/guide/npcap-users-guide.html)
2. 登录 NetScope，打开报文分析，选择已连接的 WLAN、以太网或回环接口，开始抓包。仅在自己拥有或获得授权的网络上操作。
3. 在所选接口上产生流量。回环接口可访问本机 NetScope。物理接口可访问同一局域网内的受控测速服务。切换协议、输入准确的 IP 或端口，点开任意报文检查头字段。
4. 停止后打开历史报告。SQLite 记录此次会话的起止时间、总包数、总字节数及分组汇总。筛选报文列表只改变当前视图。重启后可以查汇总，报文详情只在当前进程内可见。

从项目根目录可单独验证 Windows Npcap 和采集模块。脚本在 127.0.0.1 建立两个临时端口，用系统套接字发送 8 字节标记，按本次动态端口检查捕获的 IPv4/TCP 和 IPv4/UDP 头，最后停止抓包。测试摘要仅显示匹配数量，SQLite 使用内存数据库。

```powershell
uv run --frozen python -m scripts.verify_capture
```

本次 Windows 验证中，官方签名 Npcap 1.90 服务处于 RUNNING，Scapy 2.8.0 报告启用了 pcap。回环用例捕获 9 个匹配的 TCP 报文和 1 个 UDP 报文，脚本正常退出。另在 Windows 已连接的物理 WLAN 上用同一 Capture 实现观察 2 秒，停止时共记录 92 个真实 TCP 报文、16,439 字节。数量随主机活动变化。初次试选的物理以太网处于断开状态，没有流量；应用在启动抓包前检查链路状态。

## 用可重复的 PCAP 检查分层

从项目根目录生成已标记的合成样本。它包含文档保留地址之间的三个报文，文件仅保存在本地。

```powershell
uv run --frozen python -m scripts.make_sample_pcap .local/course-synthetic.pcap
```

在报文分析页导入文件。列表应显示 TCP、UDP、ICMP 各一个，三个报文的网络层都是 IPv4。筛选端口 443 后，TCP 详情应显示源端口 49800、序号 7、SYN 标志，IPv4 TTL 为 42。导入使用会话来源 PCAP。它不依赖本机抓包驱动，也不会更新网卡计数器。

支持未压缩的经典 PCAP 2.4，单文件上限为 8 MiB、10,000 条记录。PCAPNG 可用 Wireshark 另存为经典 PCAP。解析器检查记录长度、识别链路层，按最外层的网络头和紧随的传输或控制头分组。ICMP 错误引用的原始 TCP 头不会误计为本次 TCP 报文。协议过滤中的 IP 同时匹配 IPv4 和 IPv6。

## 数据范围

采集使用所选接口的非混杂模式。交换网络中能观察到的流量取决于本机接收的帧和驱动行为。速率来自操作系统网卡计数器，报文分析的包数和字节数来自实际被捕获或导入的报文。高负载下可能漏采，当前版本不估算驱动丢包数。

报文详情只保留最新 500 条的时间戳、地址、端口、长度和选定头字段。报文长度在经典 PCAP 中使用记录的线上长度。汇总按协议排出每类报文和字节数，端点统计给源地址和目的地址各计一次，同一地址出现两端时计一次。每次会话单独保留前 128 个不同端点，其余地址合并为“其他端点”。端点字节数相加可能超过报文字节总量。

数据库仅保留最近 100 次抓包或导入的会话汇总，其中包含本机可见的端点地址。程序正常停止时写入当前抓包会话；强行终止进程可能丢失尚未结束的当前会话。原始载荷、任意报文字段和 PCAP 文件不会写进数据库。原始 PCAP 导出未提供。账号可访问本机共享监测记录，请妥善保护本地数据库。

## 自动化覆盖

```powershell
uv run --frozen python -m pytest tests/test_packets.py -q
```

测试在内存中生成 PCAP 并验证分层、复合过滤、持久化、载荷排除、容量限制和截断文件处理。权限错误、接口断开和驱动缺失使用替身。Windows Npcap 和物理 WLAN 的独立实验见上文。
